# 1. `admin`

Pour les agents administratifs.

```sql
CREATE TABLE admin (
    id_admin INT AUTO_INCREMENT PRIMARY KEY,
    nom VARCHAR(100) NOT NULL,
    prenom VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL UNIQUE,
    mot_de_passe VARCHAR(255) NOT NULL,
    role VARCHAR(50) NOT NULL DEFAULT 'Agent',
    date_creation TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;
```

On évite donc d'avoir `admin` **et** `utilisateur` séparément.

Le `role` permet :

```text
Admin en chef
Agent
Commission
...
```

# 3. `compte`

Pour la connexion du candidat.

```sql
CREATE TABLE compte (
    id_compte INT AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(150) NOT NULL UNIQUE,
    mot_de_passe VARCHAR(255) NOT NULL,
    statut VARCHAR(30) NOT NULL DEFAULT 'En attente',
    id_candidat INT NOT NULL UNIQUE,

    CONSTRAINT fk_compte_candidat
        FOREIGN KEY (id_candidat)
        REFERENCES candidat(id_candidat)
        ON DELETE CASCADE
        ON UPDATE CASCADE
) ENGINE=InnoDB;
```

Le `statut` permet :

```text
En attente
Validé
Bloqué
```

Ça couvre votre exigence :

> le compte doit être validé avant de pouvoir candidater.

# 6. `critere`

**Très important pour le 3ᵉ collègue.**

Au lieu d'avoir tous les critères dans `offre.critere`, on les sépare.

```sql
CREATE TABLE critere (
    id_critere INT AUTO_INCREMENT PRIMARY KEY,

    id_offre INT NOT NULL,

    nom VARCHAR(150) NOT NULL,
    description TEXT,

    valeur_min DECIMAL(12,2),
    valeur_max DECIMAL(12,2),
    valeur_attendue VARCHAR(255),

    poids DECIMAL(5,2) DEFAULT 1,

    obligatoire TINYINT(1) DEFAULT 1,

    CONSTRAINT fk_critere_offre
        FOREIGN KEY (id_offre)
        REFERENCES offre(id_offre)
        ON DELETE CASCADE
        ON UPDATE CASCADE
) ENGINE=InnoDB;
```

Exemple :

```text
OFFRE : Programme d'appui aux AGR

CRITERES :

Âge
18 → 35

Résidence
Gabon

Qualification
BAC minimum

Revenu
0 → 150000
```

# 7. `piece_complementaire`

Exemple :

```text
- CV                  obligatoire
```

# 8. `piece_candidature`

⚠️ **Celle-ci manquait dans vos deux bases.**

`piece_complementaire` dit **quelle pièce l'offre demande**.

Mais il faut une table pour dire **quelle pièce le candidat a effectivement envoyée**.

```sql
CREATE TABLE piece_candidature (
    id_piece_candidature INT AUTO_INCREMENT PRIMARY KEY,

    id_piece INT NOT NULL,
    id_candidature INT NOT NULL,

    fichier VARCHAR(255) NOT NULL,
    statut VARCHAR(50) DEFAULT 'En attente',

    date_depot TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_pc_piece
        FOREIGN KEY (id_piece)
        REFERENCES piece_complementaire(id_piece)
        ON DELETE CASCADE
        ON UPDATE CASCADE,

    CONSTRAINT fk_pc_candidature
        FOREIGN KEY (id_candidature)
        REFERENCES candidature(id_candidature)
        ON DELETE CASCADE
        ON UPDATE CASCADE
) ENGINE=InnoDB;
```

Donc :

```text
piece_complementaire
        ↓
"CV obligatoire"

piece_candidature
        ↓
"C:\uploads\cv_jean.pdf"
```

# 9. `candidature`

Ta table, mais enrichie avec le numéro de candidature.

```sql
CREATE TABLE candidature (

    statut VARCHAR(50) NOT NULL DEFAULT 'En attente',

        FOREIGN KEY (id_candidat)
        REFERENCES candidat(id_candidat)
        ON DELETE CASCADE
        ON UPDATE CASCADE,

    CONSTRAINT fk_candidature_offre
        FOREIGN KEY (id_offre)
        REFERENCES offre(id_offre)
        ON DELETE CASCADE
        ON UPDATE CASCADE

```

Exemple :

```text
CAND-2026-000001
```

Ça permet de générer l'accusé de réception.

# 11. `verification`

Permet de vérifier **chaque critère individuellement**.

```sql
CREATE TABLE verification (
    id_verification INT AUTO_INCREMENT PRIMARY KEY,

    id_controle INT NOT NULL,
    id_critere INT NOT NULL,

    resultat VARCHAR(50) NOT NULL DEFAULT 'Non vérifié',

    observation TEXT,

    date_verification TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_verification_controle
        FOREIGN KEY (id_controle)
        REFERENCES controle_eligibilite(id_controle)
        ON DELETE CASCADE,

    CONSTRAINT fk_verification_critere
        FOREIGN KEY (id_critere)
        REFERENCES critere(id_critere)
        ON DELETE CASCADE
) ENGINE=InnoDB;
```

Exemple :

```text
CAND-001

Âge             → Respecté
Résidence       → Respecté
Qualification   → Respecté
Revenu          → Non respecté
```

# Répartition des 3 membres

Avec ces tables, vos trois parties deviennent beaucoup plus propres.


## Les 16 tables finales

Donc, si vous voulez une BDD **complète et cohérente pour les trois**, je partirais sur :

```text
01. admin
02. candidat
03. compte
04. dossier
05. offre
06. critere
07. piece_complementaire
08. piece_candidature
09. candidature
10. controle_eligibilite
11. verification
12. decision
13. classement
14. historique
15. orientation
16. suivi_parcours
```

**C'est cette architecture que je recommande comme base de travail commune.**

Le point important est qu'on ne crée pas `utilisateur`, `offre_service`, etc. en parallèle de tes tables actuelles : **on fusionne les fonctionnalités dans votre BDD `dglp`**, avec des noms cohérents. Cela évite que chacun développe sa partie sur des tables différentes.
